阶段 1 重组方案对比

约束: Solo 开发 + 业余时间 + 工作流引擎优先

Proposal 原方案的问题

原阶段 1 是 12 周 × 4 线并行（团队假设），单人业余下会陷入：

  • 同时学 Wails + Vue 3 + vue-flow + Go workflow — 上下文切换成本极高
  • 前端 UI 在没有后端数据时只能做 mock，后期大量返工
  • 工作流引擎是核心差异点，但被排在中间位置，前端反而先做

三种重组策略

A

引擎优先 — Engine-First

工作流引擎 → Go 骨架 → CLI/测试驱动验证 → (之后再做 UI)

Pros

  • 最快的核心价值交付——第 2 个里程碑就能看到工作流跑起来
  • 纯 Go 开发，不碰前端，上下文集中
  • CLI/test 驱动，每次推进都有可验证的产出
  • 后续加 UI 时引擎接口已稳定

Cons

  • 没有可视化界面，demo 只能在终端里跑
  • Wails 集成留到最后，可能有适配成本
B

壳先行 — Shell-First

Wails 骨架 + 最小 UI → 再填引擎 → 再完善面板

Pros

  • 从第一天就能看到桌面应用
  • Wails IPC 接口早期验证

Cons

  • 前期大量时间花在 UI mock 上，核心引擎迟迟不动
  • Vue 3 + Wails 学习曲线占用早期精力
  • 没有后端数据的 UI 开发返工率高
C

最小切片 — Thin Vertical Slice

Go 骨架 + 1 个节点 + 1 条 DAG → Wails 壳 + 1 个面板 → 连起来

Pros

  • 每个切片端到端可感知
  • 尽早发现集成问题

Cons

  • 每层都只做一点点，频繁切换语言/框架
  • 阶段 1 结束时每层深度都不够
  • 后续扩展时早期 API 可能不匹配
