三、严重问题（金融正确性优先）

按对量化产品的危害程度分 P0（致命）/ P1（重要）/ P2（建议）。金融正确性问题优先列出——量化系统中，回测失真比功能缺失更危险。

P0 · 致命问题

P0

T+1 锁定在多标的同时失效

金融正确性
位置：internal/backtest/engine_cn.go:121

问题：每个 bar 处理后执行 e.t1Lock.locked = make(map[string]float64) 清空所有 symbol 的锁定。 多 symbol 回测时，同一天处理第二个 symbol 后，第一个 symbol 当日买入的 T+1 锁定即被清除，可当日卖出——T+1 规则形同虚设。

修复：T+1 锁应以「交易日 + symbol」为键，仅在交易日切换时清空当日锁定，而非每个 bar 清空全部。 建议结构 map[tradeDate]map[symbol]qty。
P0

OMS FillOrder 卖出裁剪导致数据不一致

交易正确性
位置：internal/trading/oms.go:122-124 与 oms.go:160-161

问题：卖出时先用未裁剪的 fillQty 更新了 order.FilledQty 和 FilledAvgPrice， 随后才把 fillQty 裁剪到 pos.Quantity。导致订单记录的成交量 > 实际持仓变动，P&L 与持仓账本对不上。

修复：先裁剪 fillQty，再用裁剪后的值统一更新订单和持仓，保证两侧一致。
P0

Workflow 缓存键非确定性（map 序列化）

并发/正确性
位置：internal/workflow/cache.go:32-36

问题：CacheKey 用 fmt.Sprintf("%s:%v", nodeID, inputs) 对 map[string]any 做 %v 格式化。 Go map 迭代顺序随机，相同输入产生不同 cache key，缓存命中率极低且不可靠——可能让"幂等节点重复执行"或"命中错误结果"。

修复：对 inputs 按 key 排序后拼接，或用确定性序列化（encoding/json 对 map 会排序 key）。
P0

回测缺失涨跌停限制

金融正确性
位置：internal/backtest/engine_cn.go 全文

问题：A股 ±10%/±20%（创业板/科创板）涨跌停限制完全未实现。回测中可在涨停价买入、跌停价卖出，产生现实中不可能的交易， 系统性高估策略收益。README 宣称支持该规则但代码未落地。

修复：撮合前校验成交价是否触及涨跌停，触及则拒绝/部分成交；需区分主板/创业板/科创板/ST 的不同比例。

P1 · 重要问题

P1

无 look-ahead bias / survivorship bias 防护

金融专业性

问题：回测引擎未见显式的未来函数检测、数据对齐校验、退市股票剔除处理。CLAUDE.md 把"防 look-ahead bias"列为关键文档要求， 但实现层缺失。这是量化回测结果可信度的根基。

修复：因子/信号计算强制用 shift 防未来引用；回测加载股票池时保留退市标的；提供 point-in-time 数据访问接口。
P1

ML 训练无验证集划分（过拟合/数据泄漏）

机器学习
位置：python/src/ml/tree_engine.py:110-122

问题：训练后用同一份 X 计算 train_accuracy/train_rmse 作为评估指标，无 train/val split、无 TimeSeriesSplit、无早停。 时序数据若做随机 shuffle 会泄漏未来信息。模型注册表仅内存 self._models={}，重启即丢失，无版本/特征追踪。

修复：强制 TimeSeriesSplit 或前向滚动验证；评估指标在验证集上算；模型元数据落 SQLite。
P1

横截面因子经标准路径失效

因子有效性
位置：python/src/factor/engine.py:44 与 cross_sectional.py:33,57

问题：因子引擎先按 df[df["symbol"]==symbol] 过滤到单标的再调用因子，导致 zscore/rank 横截面因子因 x.std()==0 退化为 0/0.5， 经标准 RPC 路径根本无法工作。横截面因子是 Alpha 的核心，这是功能性失效。

修复：横截面因子需在完整截面（多标的同日）上计算，不应先过滤单标的；按因子类型分发不同计算路径。
P1

Calmar Ratio 量纲不匹配

风控正确性
位置：internal/portfolio/risk.go:94-97

问题：CalmarRatio = mean*252 / maxDD，分子是绝对收益率（如 0.15），分母 maxDD 是比例值（如 0.2）， 量纲不一致。标准 Calmar = CAGR / MaxDD，两者应同量纲。当前公式在收益率为小数时会失真。

修复：分子改用 CAGR（与 MaxDD 同为比例），或分子分母都用绝对金额。
P1

前端 ref<Map> 响应性失效

前端正确性
位置：frontend/src/stores/data.ts:57-58、workflow.ts:27

问题：用 ref(new Map()) 后调 .set() 更新，Vue 3 对 Map 的 .set() 不触发响应式更新， 导致 quotes/ohlcvCache/nodeStatuses 的变更面板感知不到——实时行情面板可能不刷新。

修复：改用 reactive(new Map())（Vue 3.4+ 支持 Map 响应式），或用普通对象/触发 .value 重新赋值。
P1

IPC 双通道未统一，wailsjs 绑定缺失

前端工程
位置：frontend/src/lib/wails.ts 仅 2 处引用，9 个文件直接用 (window as any).go.main.App.*

问题：wailsjs/ 目录不存在，Go 绑定类型未生成，IPC 入口 Call(...): Promise<any> 全程无类型。 双通道调用方式不一致，维护成本高，且丢失了 Wails 的类型安全优势。

修复：运行 wails generate 生成绑定，统一走 wailsjs 通道，移除手写 wails.ts 和 window.go 直调。

P2 · 建议改进

P2

RL 模块不完整

RLPredict 是硬编码 stub 返回固定 hold 动作（engine.py:211-217）；sac.py:19 直接 NotImplementedError； DQN 的 Sharpe 对单元素列表 std=0 退化（dqn.py:94）。README 宣称 RL×3 但实际不可用。

P2

收益率 simple/log 混用

因子全用简单收益 pct_change，而 garch.py docstring 声称 "log returns" 却不做变换，依赖调用方——存在混用隐患，跨模块累计会出错。

P2

魔法数字散落 + goto 语句

252（年交易日）、0.0005（印花税）、0.0003（佣金）、256（缓存）、5000（busy_timeout）散落各处未提为命名常量； backtest 中 3 处 goto recordEquity 属代码异味，建议结构化控制流替代。

P2

数据适配器缺少统一限流/超时

仅 EastMoney 有限流（500ms+jitter），其余 30 个适配器各自 http.Client 无统一 Timeout。被风控/封 IP 风险高。建议在 AdapterRegistry 层统一注入限流器和超时。

P2

版本号与元数据不一致

go.mod 声明 go 1.26.4（该版本不存在，疑为笔误，应为 1.22.x）；config.yaml 版本 0.0.1 与 README 2026.6.19 不符； README 与 CLAUDE.md 对目录结构描述不一致（internal/ 在根 vs 在 app/ 下）。

P2

Python 缺工具链 + 双虚拟环境

无 mypy/ruff/flake8 配置，无静态检查约束；存在 .venv 与 venv 两个重复虚拟环境目录；pyproject.toml 与 requirements.txt 不同步。

P2

HK/CRYPTO 回测引擎缺失

README 宣称 CN/US/HK/CRYPTO 四市场回测，但仅 CN/US 有实现，HK（T+2/港股通）和 CRYPTO（资金费率/强平）未落地。US 的 PDT 规则仅"信息性"空操作。

P2

前端 WorkflowCanvas 双数据源 + 边匹配缺陷

画布维护本地 nodes/edges ref 并 watch 拷贝 store，双真相易失步；fromWorkflowJSON 边匹配按 nodeType 而非 id，同类型多节点必然错连； undo/redo 用 JSON 深拷贝大图性能差。

按优先级排序，先修正确性，再补功能，最后打磨工程。

5

工程打磨（持续）

魔法数字提常量、goto 重构、适配器统一限流/超时、Python 引入 ruff+mypy、统一版本号与目录文档、补齐 RL 或从 README 移除声明。

五、总结

QuantFlow 是一个架构成熟、工程纪律严明的量化金融终端项目。作为桌面级单用户应用，它的技术选型（Go+Wails+SQLite+Python gRPC） 每一项都有清晰的 rationale，分层干净、无循环依赖、测试覆盖在同类项目中名列前茅，Spec-Before-Code 的开发流程体现了专业团队的素养。

然而，从一个量化金融产品的视角，它存在几处致命的正确性问题：T+1 锁定在多标的回测中失效、涨跌停完全缺失、OMS 成交量与持仓账本不一致、 无 look-ahead/survivorship bias 防护、ML 训练无验证集划分。这些问题会让回测结果系统性失真——而量化系统的核心价值正是回测可信度。 用一句话概括：工程骨架是 9 分水准，金融血肉是 6 分水准，把 P0 四项修掉，这个项目就能从"演示级"跨入"可用级"。

建议优先级：P0 金融正确性 > bias 防护 > 前端响应性 > 补齐市场引擎 > 工程打磨。修复 P0 后建议重新评审，确认回测结果在已知 case 下与预期一致。
