## 1. 执行摘要

QuantFlow Terminal 是一个极具野心的双模式量化金融终端项目，将 Bloomberg 风格面板终端与可视化工作流编排融于一身。技术栈为 Go + Wails v3 + Vue 3 + SQLite + Python gRPC sidecar，覆盖 A 股 / 港股 / 美股 / 加密四个市场。

**一句话结论**: 这是我（们）见过的 solo 开发者量化金融项目中最 impressive 的一个——也是 scope 最大、LICENSE 策略最阻碍采用、回测科学与财务数学最需要大修的 prestine 代码库。

### 核心数据

| 指标 | 数值 | 评价 |
|------|------|------|
| 后端包 | 14 internal packages | 健康 |
| 前端面板 | 53 Vue 组件 | **严重超纲** |
| 工作流节点 | ~90 Go 文件 | 丰富但部分未实现 |
| 数据适配器 | 30+ 个 | 质量参差 |
| 测试文件 | 476+（Go + Vue + Python） | 覆盖面好，但深度不够 |
| 文档 Spec | 54 个 markdown 文件 | 业界罕见的规范程度 |
| 贡献者 | 1 人 | **最高风险** |
| 开发周期 | ~72 小时（101 commits） | 令人惊叹但也令人担忧 |

### 三大红色警报

1. **🔥 回测中存在前瞻偏差**（量化金融专家）：所有回测均在同一根 K 线的 Close 价上生成信号并执行，这是致命的科学错误
2. **🔥 AGPL 许可证阻碍采用**（营销专家）：对于桌面应用，AGPL 吓退所有严肃用户，且无法获得商业授权的收益
3. **🔥 53 个面板的 scope 失控**（三方共识）：v1 应有的 15-20 个面板被 53 个稀释，维护性存疑

## 3. 量化金融专家评审

### 3.1 关键发现

#### 🔴 致命：回测前瞻偏差

**文件**: `internal/backtest/runner.go` lines 103-117, 140, 198

**问题**: 信号生成和执行在 **同一根 K 线** 上完成。策略在 `bar[t].Close` 上生成信号，立即以 `bar[t].Close (1 ± slippage)` 成交。

```
For each bar t:
  Signal(t)  ← 使用 bar[t].Close
  Fill(t)    ← 以 bar[t].Close 成交
```

**现实情况**: 基于今日收盘价的信号只能在次日开盘执行。当前实现相当于让策略"预知"收盘价，**所有回测结果都会过于乐观**。

**行业正确做法**: `Signal(t) → Execute at bar[t+1].Open`

`order_matcher.go` 中已经包含了正确的市价单成交逻辑（使用 bar.Open），但回测引擎直接绕过了它，手动计算 `effectivePrice = bar.Close * (1 + slippage)`。

**严重程度**: ⚠️ 最高。所有使用该回测系统的策略结果不可信。

---

#### 🔴 致命：无复权处理/公司行动

**整个代码库缺失**。

- 没有**复权价格**（adjusted close）——任何跨股息日或拆股的 K 线数据都会显示错误 PnL
- 没有**股息累积**——总回报 vs 价格回报
- 没有**拆股/并购**处理——被收购公司的持仓者在回测中会显示为"归零"

**严重程度**: ⚠️ 最高。任何超过数月的回测结果均不可靠。

---

#### 🔴 致命：A 股涨跌停未实现

**文件**: `internal/backtest/engine_cn.go`（docstring 提到 ±10%/±20% 但无实现）

涨停板时无法买入，跌停板时无法卖出。但当前回测引擎会以 `Close + slippage` 成交，即使这个价格在当天技术上不可达。

对于 A 股的动量/突破策略，这会产生严重误导。

---

#### 🟡 严重：Sharpe Ratio 公式错误

**文件**: `internal/backtest/metrics.go` lines 61-82

**两个版本的 Sharpe Ratio，都是错的**:

1. **metrics.go:64**: `sharpe = CAGR / annualVol`
   - CAGR 是几何收益率，Sharpe 需要算术平均——总是低估
   - 无风险利率硬编码为 0

2. **portfolio/risk.go:74**: `(mean * 252 - riskFreeRate) / annualVol`
   - 这个版本用了算术平均（正确），但标准偏差用了 `n` 而非 `n-1`（Bessel 校正缺失）

**Sortino Ratio 分母错误**: 下行方差除以 `downCount`（负收益天数）而不是总天数 `nDays`，导致高估下行风险、低估 Sortino。

---

#### 🟡 严重：多标的回测逻辑错误

**文件**: `internal/backtest/runner.go`

当多个股票在同一日期有 K 线时：
1. 每根 K 线独立处理
2. 每处理一根 K 线就记录一次净值（同一日期多条记录）
3. `ComputeMetrics` 在同一天的多笔净值之间计算"日收益"，产生荒谬结果

**系统当前只支持单标的回测**。

---

#### 🟡 严重：无幸存者偏差保护

代码库中没有提及幸存者偏倚。免费数据源通常只包含仍然存活的股票，退市/破产的股票被排除，系统性地高估了回测收益 2-5%/年。

---

#### 🟡 中等：Win Rate / Profit Factor 统计错误

`computeTradeStats` 函数中：
- 买入交易的 PnL=0（未设置），被静默丢弃
- 部分成交产生多条卖出记录，每条被计为独立交易
- 没有 round-trip 配对逻辑

---

#### 🟡 中等：美股 PDT 规则计数错误

代码统计"一天内有 ≥2 笔交易的天数"，但正确的 PDT 规则是"同一天内对同一标的做买入+卖出"。当前实现会误计数。

---

#### 🟡 中等：无对标基准的指标

config.go 中定义了 `Benchmark string` 但从未使用。缺少：
- Information Ratio（超额收益/跟踪误差）
- Beta / Alpha
- Tracking Error
- Up/Down Capture
- 换手率
- IC（信息系数）

---

#### 🟡 中等：VaR 符号约定相反

`risk.go:100`: VaR 计算为负值（如 -2300），但行业惯例报告为正值（损失 $2,300）。

---

#### 🟡 中等：凯利公式硬编码

`position_sizer.go` 中 winLossRatio 硬编码为 1.0，实际退化为固定百分比分配。

## 4. 市场营销专家评审

### 4.1 定位与信息传递

#### 核心问题：定位混淆

- **中文 README** 清晰有力：「双模式量化金融终端 — 彭博式面板终端 × 可视化工作流编排」
- **英文 README** 声称 18 panels（实际 53），承诺过多但证据不足
- **"Bloomberg-Style" 比较有风险**——Bloomberg 是 $24K/年的机构标准，一个 Wails 桌面应用可比性有限

**建议**: 从问题出发，而非功能。例如：  
> "别再在 TradingView 看图表、QuantConnect 做回测、Python 跑脚本之间来回切换。QuantFlow 给你一个桌面应用：终端看实时数据，工作流做策略研究。"

#### 目标用户不明确

| 可能的用户 | 适合度 | 原因 |
|-----------|--------|------|
| 中文零售量化交易者 | ✅ 最匹配 | A 股优先、中文文档、EastMoney 等数据源 |
| 中国金融学生/研究人员 | ✅ 匹配 | 一站式工具包 |
| 全球零售量化交易者 | ⚠️ 中等 | 英文文档落后、A 股偏重 |
| 对冲基金/机构 | ❌ 不匹配 | 安全性、审计、合规都不满足 |

**建议**: 明确 ICP（理想客户画像）：中文零售量化交易者（25-40 岁，懂技术，管理 5 万-500 万 RMB）

### 4.2 ⚠️ 最大营销失误：AGPL-3.0 许可证

AGPL 是桌面应用的**灾难性许可选择**：

| 用户类型 | AGPL 影响 | 预期行为 |
|---------|-----------|---------|
| 零售用户（爱好者） | 不关心 | ✅ 会用 |
| 严肃零售用户（有策略 IP） | 担心策略被迫开源 | ❌ **不会用** |
| 自营交易公司 | 法务直接拒绝 | ❌ **不会用** |
| 对冲基金 | 同上 + 合规问题 | ❌ **不会用** |
| 大学/研究机构 | 可能接受 | ⚠️ 可能用 |

**建议**: 切换到 Apache 2.0 或 GPL-3.0。如需商业化路径，使用双许可（AGPL 免费 + Commercial 付费）。

### 4.3 Scope 失控：53 panels 是 v2 的 scope

**三方共识**: v1 应该 15-20 个面板 + 20 个节点，全部经过完善的测试。

| 实际 | 建议 |
|------|------|
| 53 面板 | 15-20 个精良的面板 |
| ~90 节点 | 20 个覆盖 80% 场景的节点 |
| 30+ 适配器 | 每市场 3 个生产级适配器 |
| 卫星/地缘政治/预测市场 | 移入「实验性」文件夹 |

**53 面板意味着 53 个潜在的断裂点**。一个 solo 开发者无法长期维护。
